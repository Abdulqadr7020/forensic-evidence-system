# Plan 11-01: Frontend Modal Integration & Verified Cryptographic Pipeline

## Objective
Connect the frontend Ingest Evidence Modal, Documents view, and Verification modals to the backend cryptographic API (`server/index.ts`). Implement real-time multi-step cryptographic progression in the ingestion modal, direct verified streaming downloads with tamper alerts, server-side decrypted evidence listing, and automated Merkle checkpoint sequence progression.

## Dependencies
- Backend Express server running on port 3001 (`server/index.ts`).
- Supabase tables (`cases`, `evidence`, `merkle_checkpoints`) and storage bucket (`evidence-vault`).
- Frontend components: `IngestEvidenceModal.tsx`, `DocumentsView.tsx`, `EvidenceFolderCard.tsx`, `VerificationResultModal.tsx`, `src/services/db.ts`.

## Tasks

### 1. Backend Endpoint Enhancements (`server/index.ts`)
**Description:** Expand the Express server to support complete frontend cryptographic workflows:
1. **Evidence Listing Endpoint (`GET /api/evidence`):**
   - Query all rows from Supabase `evidence` table ordered by `created_at DESC`.
   - Decrypt field-encrypted `title` and `description` using `decryptField` from `server/crypto.ts`.
   - Parse IV and authentication tag from stored format (`gcm:iv:tag:ciphertext`).
   - Query case numbers from `cases` table to enrich records.
   - Return structured documents array compatible with frontend `DocumentRecord` type.
2. **Enhanced Ingestion Endpoint (`POST /api/evidence/upload`):**
   - Calculate server-side Merkle leaf hash: `merkleLeafHash = sha256(encryptedFile.sha256Ciphertext + fileId)` (`D-13`).
   - Query latest sequence from `merkle_checkpoints` table, calculate new root hash, and insert updated checkpoint record (sequence #105, incremented `leaf_count`) (`D-14`).
   - Update `cases` table: increment `document_count = document_count + 1` and set `last_activity_at = NOW()` for `case_id` (`D-11`).
   - Return complete cryptographic receipt payload (`evidenceId`, `storagePath`, `hashes: { sha256Plaintext, sha256Ciphertext }`, `merkleLeafHash`, `checkpointSequence`, `iv`, `authTag`, `fileSizeBytes`, `title`, `caseId`).
3. **Download Filename & Tamper Handling (`GET /api/evidence/:id/download`):**
   - Decrypt title and set `Content-Disposition: attachment; filename="{originalName}"` (`D-06`).
   - Return HTTP 400 with `{ error: 'TAMPER_DETECTED' }` if GCM authentication tag verification fails (`D-07`).
**Expected Outcome:** Express API fully powers all frontend evidence listing, ingestion receipts, filename preservation, and Merkle checkpoint updates.

### 2. Real-Time Cryptographic Ingestion Modal (`IngestEvidenceModal.tsx`)
**Description:** Transform `IngestEvidenceModal` into an authenticated zero-trust ingestion pipeline:
1. **Dynamic Case Loading:**
   - Fetch active cases dynamically using `fetchCases()` from `src/services/db.ts` (`D-10`).
   - Populate select dropdown with real case numbers and titles.
2. **Multipart Upload & Animated Stepper:**
   - Submit form data to `http://localhost:3001/api/evidence/upload`.
   - Render animated stepped progress cards (`D-01`, `D-02`):
     - Step 1: Plaintext SHA-256 Digest Calculation.
     - Step 2: AES-256-GCM Encryption (12-byte CSPRNG IV + 16-byte Tag).
     - Step 3: Ciphertext SHA-256 Digest Calculation.
     - Step 4: Supabase Vault & Database Leaf Commitment.
   - Pace step transitions (~350ms per step) for visual verification.
3. **Cryptographic Ingestion Receipt View:**
   - On completion, transition to receipt screen displaying permanent Evidence ID, Merkle leaf hash, IV/Tag, and action buttons: "Copy Proof" and "Done" (`D-03`).
4. **Step Failure & Retry State:**
   - On network or server error, mark the specific failing step with a red alert badge and error message, preserving form inputs for retry (`D-04`).
5. **State Update:**
   - Call `onDocumentCreated` with the returned document receipt to optimistically append to the local registry (`D-12`).
**Expected Outcome:** IngestEvidenceModal displays animated real-time cryptographic feedback and outputs a verified ingestion receipt.

### 3. Data Service & Documents View Integration (`src/services/db.ts` & `DocumentsView.tsx`)
**Description:** Connect `DocumentsView` to live decrypted evidence records and implement direct verified downloads:
1. **Update `src/services/db.ts`:**
   - Update `fetchDocuments()` to fetch from `http://localhost:3001/api/evidence`, falling back to Supabase/fixtures if offline.
   - Update `fetchCheckpoints()` to fetch latest checkpoint sequence from Supabase `merkle_checkpoints` table.
2. **Direct Evidence Download Action (`DocumentsView.tsx` & `EvidenceFolderCard.tsx`):**
   - Add a direct download button to each row and folder card (`D-05`).
   - Trigger `GET http://localhost:3001/api/evidence/:id/download`, streaming the decrypted bytes and saving with the server-supplied filename (`D-06`).
   - Display a success toast: "Evidence Decrypted & Verified: AES-256-GCM authentication passed".
3. **High-Severity Tamper Alert Modal:**
   - If download returns HTTP 400 `TAMPER_DETECTED`, display a red glassmorphic security alert modal warning that ciphertext tampering was detected (`D-07`).
4. **Optimistic Prepend:**
   - Prepend newly ingested evidence to `documents` state immediately upon receipt close (`D-12`).
**Expected Outcome:** DocumentsView lists real decrypted evidence, provides one-click streaming downloads, and defends against tampering.

### 4. Cryptographic Proof Inspection & Merkle Sequence Synchronization (`VerificationResultModal.tsx` & Global State)
**Description:** Enhance cryptographic proof verification and ledger sequence indicators:
1. **Enhanced Proof Card in `VerificationResultModal.tsx`:**
   - Display verified cryptographic parameters: AES-256-GCM status, 12-byte IV hex, 16-byte Auth Tag hex, Plaintext SHA-256, Ciphertext SHA-256 (`D-08`).
   - Provide copy-to-clipboard buttons for each hash and tag.
   - Verify Merkle leaf hash against the active checkpoint sequence and root hash (`D-16`).
2. **Global Checkpoint Pulse & Integrity View Sync:**
   - Update header and `IntegrityView` checkpoint sequence indicator to #105 upon upload commit with a subtle glowing pulse animation (`D-15`).
**Expected Outcome:** Full cryptographic transparency across the verification modal and global ledger sequence badges.

### 5. Automated E2E Verification & Type Check
**Description:** Author an automated end-to-end test script `server/test-phase11-e2e.ts` and run type checking:
1. Script uploads a sample evidence file via `POST /api/evidence/upload`.
2. Verifies HTTP 201 with `merkleLeafHash`, sequence #105, IV, and auth tag.
3. Verifies `cases` table incremented `document_count`.
4. Queries `GET /api/evidence` and verifies decrypted title and metadata match.
5. Downloads via `GET /api/evidence/:id/download` and verifies plaintext integrity and filename header.
6. Downloads a tampered file and verifies HTTP 400 `TAMPER_DETECTED`.
7. Run `npm run build` or `npx tsc --noEmit` to verify zero TypeScript compilation errors.
**Expected Outcome:** All cryptographic, database, API, and frontend contracts are 100% verified.

## Definition of Done
- `POST /api/evidence/upload` increments case document count, computes Merkle leaf, and updates checkpoint sequence in Supabase.
- `GET /api/evidence` serves decrypted evidence records with cryptographic proofs to the frontend.
- `IngestEvidenceModal` displays animated stepped progression (~350ms each) and completes with a cryptographic receipt view.
- `DocumentsView` and folder cards provide direct one-click verified downloads preserving original filenames.
- Tamper detection halts corrupted file downloads and surfaces a high-severity security alert dialog.
- `VerificationResultModal` displays real IV, Auth Tag, Plaintext & Ciphertext hashes with live invariant checks.
- E2E script and TypeScript checks pass cleanly.
